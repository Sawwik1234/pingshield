# PingShield

**Защита игроков с очень высоким пингом (3000–5000 ms) для Paper / Purpur / Folia 26.1.2.**
Автор: **Sawwik** · Java 25 · api-version `26.1` · `folia-supported: true` · версия 1.5.0

> **Идея:** пока пинг игрока выше порога, он **бессмертен**, но **не может ничего**: не двигается,
> не бьёт, не ломает, не использует предметы, не подбирает лут, не открывает инвентарь,
> не телепортируется. Никакого `GM1` и никакого креатива — игрок остаётся в своём режиме игры,
> а неуязвимость даёт **флаг неуязвимости сущности** + отмена событий урона.

## 2. Что именно делает защита

| Действие игрока | Пока активна защита |
|---|---|
| Любой урон по игроку (PvP, мобы, падение, лава, взрывы, снаряды, эффекты) | **Отключён** (`setInvulnerable(true)` + отмена событий) |
| Урон **от** игрока (руками, снарядами, поставленным TNT, зельями) | Отключён — лаг не должен быть преимуществом |
| Урон от питомцев (волки, кошки, големы) | Отключён |
| Движение (ходьба, бег, прыжок, полёт, элитра) | Заблокировано; позиция удерживается на «якоре» |
| Удар, использование предметов, выбрасывание, смена слота, еда, смена рук | Заблокировано |
| Ломать/ставить блоки, вёдра, сбор урожая, книга с кафедры, кровать, рыбалка | Заблокировано |
| Сундуки, люки, кнопки, верстаки, **свой инвентарь** | Заблокировано |
| Подбор предметов | Заблокировано |
| Телепорт (портал, эндер-жемчуг, `/tp` от плагина) | Заблокировано |
| Взаимодействие с сущностями (торговля, стойки, седло) | Заблокировано |
| Команды в чат | **Разрешены** (нужно позвать админа; блокировка — опция `interactions.commands.block`) |

Плюс: мобы перестают видеть игрока целью; игрока высаживает из транспорта; огонь тушат;
высота падения сбрасывается; сытость за время заморозки возвращается обратно.

## 3. Дыры в логике, которые были найдены и закрыты

| № | Дыра | Как закрыта |
|---|---|---|
| 1 | **Нельзя замораживать одним мгновенным замером** — пинг даёт одиночные спайки | решение по EWMA-сглаживанию + серии подтверждений (`enter/exit-confirm-samples`) |
| 2 | **«Мигание» защиты** на грани порога | гистерезис + минимальное время удержания `min-protect-seconds` |
| 3 | **Лаг сервера ≠ лаг игрока**: при лагах у всех сразу пинг скачет, и весь онлайн стал бы статуями | `server-lag-guard` по TPS и доле игроков |
| 4 | **Пинг за прокси** (Velocity/Bungee) показывает путь до прокси, а не до игрока | авто-детект локального входа → автозащита отключается, режим `proxy.mode` |
| 5 | **Новый игрок замирал на спавне** (пинг ещё не измерен) | `join-grace-seconds` + сброс состояния на входе |
| 6 | **Игрок выключал полёт двойным пробелом** и падал | отмена `PlayerToggleFlightEvent` (режим `FLY`) |
| 7 | **Пистоны/взрывы/пушки сдвигали «замороженного»** | отмена `PlayerVelocityEvent` + возврат на якорь через `teleportAsync` |
| 8 | **Взрывы разрушали окружение, пока игрок заморожен** | заморозка + защита от урона; телепорт-возврат нейтрализует отброс |
| 9 | **Смерть при снятии защиты**: пинг в норме, а игрок висит над лавой / горит / тонет | `extend-in-danger`: удержание до 15 с + `SLOW_FALLING`/`FIRE_RESISTANCE` |
| 10 | **Урон от падения после «зависания»** | сброс `fallDistance`, `fall-damage-grace-ms`, эффект Slow Falling |
| 11 | **«Лаг = чит»**: бессмертие + возможность бить | исходящий урон заблокирован, питомцы тоже |
| 12 | **Вечное бессмертие искусственным лагом** | `max-protection-seconds` + пауза + лимит активаций в час |
| 13 | **Хронически плохой провайдер** (скачущий пинг всегда) | политика `IMMUNITY_ONLY`: щит **без** заморозки, чтобы не дёргать игрока |
| 14 | **Смена GameMode** (админ переключил в наблюдателя / креатив) | реакция на `PlayerGameModeChangeEvent`, снятие/перезаморозка |
| 15 | **Хардкорный античит-сервер**: защита в бою = злоупотребление | `combat.prevent-protection` (защита в бою не включается) и боевой тег |
| 16 | **Падение в пустоту** и `WORLD_BORDER` | по умолчанию в `damage.incoming.exceptions` — защита не работает вечно в пустоте |
| 17 | **Сторонний плагин телепортировал игрока** (арена, варп) | блокировка телепортов + сдвиг якоря (`refreshAnchor`) |
| 18 | **Сервер с NPC** (Citizens) | фильтр по метаданным `NPC` |
| 19 | **Сброс состояния другими плагинами** (walk-speed, полёт) | повторное «до-замораживание» каждые `enforce-interval-ticks` |
| 20 | **Утечки памяти** (карты по вышедшим игрокам) | очистка на выходе + периодическая чистка |
| 21 | **Ошибка в одном игроке убивала весь цикл** (упавшая repeating-задача не перезапускается) | весь цикл в `try/catch` |
| 22 | **Отсутствие наблюдаемости** («а что происходит?») | `/pingshield profile`, `/pingshield perf`, `audit.log` |
| 23 | **Урон/падение по игроку после смерти и респавна** («залипшая» заморозка) | снятие защиты на death/respawn и восстановление состояния |
| 24 | **«Ничего не может» ≠ «ничего не делает»**: оставались инвентарь, лут, хотбар, рыбалка, свой инвентарь, телепорты | всё перечисленное заблокировано |

## 4. Ответ на «нужна рефлексия и NMS»

Не нужны. Всё сделано на публичном API Paper/Folia 26.1.2:

* неуязвимость — `Entity#setInvulnerable(boolean)`;
* удержание позиции — отмена `PlayerMoveEvent` / `PlayerVelocityEvent` + `Entity#teleportAsync`
  (обычный `teleport` на Folia запрещён);
* «якорь» и скорости — `Player#getWalkSpeed/setWalkSpeed`, `getFlySpeed/setFlySpeed`;
* индикация — Adventure `sendActionBar` / `BossBar`;
* планирование — `GlobalRegionScheduler`, `EntityScheduler`, `AsyncScheduler`, `Bukkit.isOwnedByCurrentRegion`;
* журнал — `AsyncScheduler` + `Files.writeString`.

Единственное место, где NMS мог бы понадобиться, — если кто-то захочет «замораживать» игрока
на уровне пакетов (cancel `ServerboundMovePlayerPacket`). Практической необходимости нет:
`PlayerMoveEvent` + флаг неуязвимости дают тот же результат без привязки к версии сервера.

## 5. Ответ на «куча проверок = нагрузка, а если провайдер плохой и пинг скачет всегда?»

### Нагрузка (замеры, а не обещания)

Горячий путь — один проход по онлайну раз в `check-interval-ticks` (по умолчанию 20 тиков = 1 с).
На игрока: `Player#getPing()` (чтение int), математика EWMA/jitter, один `ConcurrentHashMap.get`.
**Аллокаций в цикле нет**, состояние пишет единственный поток — синхронизация не нужна.

Замер на этой машине (`./gradlew simulate`):

```
sample(): 6.95 нс на вызов
То есть: 200 игроков раз в секунду ≈ 1.4 мкс/с на весь сервер
```

Для сравнения: один тик сервера — 50 000 000 нс. Замер на живом сервере: `/pingshield perf`
(среднее/пиковое время цикла, нс на игрока, TPS, heap).

Что специально вынесено из горячего пути:

* тяжёлые действия (заморозка, индикатор, звук, сообщения) — только при старте/снятии защиты
  и далее раз в `perf.enforce-interval-ticks` (10 тиков);
* права (`hasPermission`, в т.ч. LuckPerms) — кэш на 30 с, а не каждый тик;
* NPC/мир/режим игры проверяются только для кандидатов (у кого EWMA перевалил порог),
  а не для всех подряд;
* аудит пишется асинхронно.

### Плохой провайдер (пинг скачет всегда)

Пять уровней защиты от ложных срабатываний:

1. **EWMA-сглаживание** (`ping.smoothing`) — одиночный спайк не морозит;
2. **серии подтверждений** — `enter-confirm-samples: 2`, `exit-confirm-samples: 3`;
3. **минимальное удержание** `min-protect-seconds: 5` — заморозка не мигает;
4. **подавление jitter**: при шуме выше `jitter-threshold-ms` порог входа поднимается на
   `jitter-enter-bonus-ms` — «скачущий пинг» сам по себе не причина морозить;
5. **`abuse.chronic-policy`** — что делать с тем, кто лагает постоянно:
   `LIMITED` (не защищать), `PROTECT` (защищать всегда) или `IMMUNITY_ONLY`
   (**щит без заморозки**: играет как обычно, урон в обе стороны отключён).

С версии 1.5.0 к этому добавились три отдельных детектора — искусственный лаг, пинговый шторм
по подсетям и политика длительного лага (см. §12). По умолчанию все они **наблюдающие**:
пишут в `audit.log` и уведомляют персонал, никого не наказывая.

Результат симуляции (1 прогон = 1 час, «мигание» = защита короче 10 с):

| Сценарий | Наивно (по сырому пингу) | PingShield |
|---|---|---|
| Плохой Wi-Fi: база 220 ms + одиночные всплески до 7 s | 101 заморозка, 101 мигание | **50 заморозок**, 50 миганий |
| Плохой мобильный канал: 380 ms, скачки 200–4500 ms | 170 заморозок, 170 миганий | **6 заморозок**, 6 миганий |
| Реальный обрыв: 200 ms → 4500 ms на 45 с | 1 заморозка | 1 заморозка (игрок спасён) |
| Хронический лаг: стабильно 3500 ms | 100 % времени в защите | 100 %, но с лимитом, паузой и счётчиком `abuse.chronic-ping` |
| Нормальный канал: 40–120 ms | 0 | 0 |

## 6. Команды и права


## 8. Что стоит знать и подстроить под себя

* **`damage.incoming.exceptions`** по умолчанию `[VOID, WORLD_BORDER]`. Это сознательно:
  иначе игрок, попавший в пустоту, получил бы бессмертие до конца лимита. Если нужна
  «абсолютная» неуязвимость — очистите список.
* **Прокси.** За Velocity/Bungee реальный пинг игрока известен только прокси. В режиме `AUTO`
  плагин это обнаружит и выключит автозащиту. Правильное решение для прокси — плагин на стороне
  Velocity (там `Player#getPing()` — это пинг до игрока) и передача сигнала на backend через
  plugin messaging. Каркас для этого в PingShield есть (`proxy.mode`), интеграция — следующий шаг.
* **Режим `FLY`** оставлен как опция, но по умолчанию выключен: он самый заметный и может
  раздражать клиентские античиты. Для «просто застыл, но бессмертен» используйте `PASSIVE`.
* **Аудит.** Все входы/выходы из защиты, удержания в опасности и ручные действия пишутся
  в `plugins/PingShield/audit.log` (асинхронно) — удобно разбирать жалобы «меня убили в лаге»
  и ловить злоупотребления.

## 9. Интеграция с CoreProtect (логи)

Подключение — **soft-depend**: если CoreProtect не установлен, плагин работает как обычно.
Если установлен и его API включён (`api.enabled` в конфиге CoreProtect), включаются две вещи:

1. **Маркеры в логах.** При входе/выходе из защиты PingShield пишет запись в лог CoreProtect
   (`CoreProtectAPI#logChat`): `[PingShield] защита от лагов ВКЛ: пинг 4210 ms (порог 3500 ms)`.
   Администратор, делающий `/co lookup` на «странном» месте, сразу видит, что игрок в этот момент
   стоял из-за пинга, а не прятался и не читерил.
2. **Проверка изменений вокруг игрока.** Когда защита снимается, одним запросом читаются
   изменения блоков вокруг «якоря» за время защиты. Если блоки трогали **другие** игроки —
   это классический гриф по лагающим (пока игрок висел, под ним копали, его застраивали,
   ломали дверь) — событие попадает в `audit.log`, а персонал (`pingshield.notify`) получает
   уведомление с готовой командой `/co lookup u:<ник> t:10m r:3`.
3. **Ручной отчёт:** `/pingshield cp <игрок> [минут] [радиус]` — то же самое по запросу.

### Как встроить поиск PingShield в сам CoreProtect

CoreProtect не позволяет добавить собственный «тип данных» — схема базы фиксирована. Но у него есть
параметр **`f:<filter>`**, который фильтрует **текст по префиксу** (`/co lookup a:chat f:/ban`).
Поэтому каждое событие пишется маркером с устойчивым тегом:

```
[PingShield/START]    защита от лагов ВКЛ: пинг 4210 ms (порог 3500 ms)
[PingShield/END]      защита ВЫКЛ: PING_OK, длительность 42 с
[PingShield/IMMUNITY] щит без заморозки включён
[PingShield/HOLD]     удержание: опасное место, осталось 9 с
[PingShield/CP]       рядом меняли блоки: Alex (12), Steve (3)
```

И теперь всё ищется **родными командами CoreProtect**, без каких-либо плагинов-посредников:

| Задача | Команда |
|---|---|
| Все события PingShield за час | `/co lookup a:chat f:[PingShield] t:1h` |
| Только входы в защиту | `/co lookup a:chat f:[PingShield/START] t:1d` |
| События конкретного игрока | `/co lookup u:Steve a:chat f:[PingShield] t:6h` |
| Только количество, без вывода | `/co lookup a:chat f:[PingShield] t:2h #count` |
| Кто копал рядом с защищённым | `/co lookup u:Steve t:30m r:5` |
| Стоя рядом с местом: всё в радиусе | `/co lookup t:2h r:10` |
| Кто лазил в сундуки рядом | `/co lookup u:Steve a:container t:30m r:5` |

Тег настраивается: `integrations.coreprotect.marker-tag` (без пробелов и запятых — запятая
в `f:` разделяет несколько префиксов).

### Кнопки в чате = нативный поиск в один клик

В `/pingshield cp <игрок>` и `/pingshield search [минут] [радиус]` плагин выдаёт **кликабельные
кнопки** (Adventure `ClickEvent.runCommand`): клик запускает `/co lookup …`, наведение показывает
саму команду. Уведомления персоналу о «грифe по лагающим» тоже приходят с такой кнопкой —
админ кликает и сразу видит выборку CoreProtect. Команды, требующие радиуса, используют позицию
**того, кто кликает**, поэтому кнопку нужно нажимать на месте происшествия (или выделить регион
через WorldEdit и искать с `r:#we`).

Опционально: `integrations.coreprotect.log-interaction: true` ставит запись взаимодействия
в точке удержания — тогда защищённые игроки видны и в географическом поиске
`/co lookup a:click r:10 t:2h` (цена — +2 строки в базе CoreProtect на каждую защиту).

> Если в CoreProtect отключено логирование чата (его `config.yml` → `logging`), маркеры
> не запишутся. Проверить просто: `/co lookup a:chat t:5m` сразу после того, как кто-то
> попал под защиту.

### Совместимость версий API CoreProtect (проверено)

| Что | 22.x / 24.1 (то, что опубликовано в Maven) | 25.0+ (master, API v13) |
|---|---|---|
| Area-запрос по области (наш путь) | ✅ `performLookup(int,List,List,List,List,List,int,Location)` | ✅ тот же метод (строка 777 в `CoreProtectAPI`) |
| Типизированный area-lookup | ❌ отсутствует (`blockLookup(LookupOptions)` нет) | ✅ `blockLookup(LookupOptions)` |
| Типизированный по одному блоку | ✅ `blockLookup(Block, LookupOptions)` | ✅ |

**Почему выбран «сырой» area-запрос, а не типизированный API.** Типизированный вызов в 24.1
требует объект `Block` — то есть запрос на каждый блок отдельно (радиус 3 = 343 запроса вместо
одного), и вдобавок `Block`/`BlockState` нельзя безопасно читать из асинхронного потока
(на Folia это прямой путь к порче данных). Area-запрос лишён обоих недостатков и жив
в API начиная с 22.x и по 25.0+ включительно. Результат разбирается через публичный
`CoreProtectAPI.ParseResult` (`getTimestamp/getPlayer/getActionString/getType`).
Все запросы выполняются в `AsyncScheduler` — тики сервера не блокируются.
Если CoreProtect будущих версий уберёт этот метод, плагин не упадёт: маркеры продолжат
работать, а в лог уйдёт понятное предупреждение.

Зависимость для компиляции: `compileOnly("net.coreprotect:coreprotect:24.1")` (репозиторий
`https://maven.playpro.com`). На сервере версия CoreProtect может быть любой актуальной —
класс-лоадер берёт реализацию оттуда, а не из нашей сборки.

## 10. ViaVersion / ViaBackwards: что это меняет

На ядре **26.1.2** клиенты **1.21.4 и ниже — это старые клиенты на новом сервере**, их пускает
**ViaBackwards** (ViaVersion сам по себе пускает только клиенты *новее* ядра, например 26.2/26.3).
PingShield учитывает это так:

| Аспект | Что происходит |
|---|---|
| Точность пинга | `Player#getPing()` — RTT keep-alive пакетов этого соединения. Via его **не искажает**, значение реальное, пороги работают корректно |
| Джиттер | Трансляция протокола добавляет серверу работы → у старых клиентов чаще «пилообразные» скачки. Для клиентов, чей протокол ≠ протоколу сервера, порог входа автоматически **выше** на `integrations.via.extra-threshold-ms` (по умолчанию +500 ms) |
| Определение версии | Публичный Paper-интерфейс `NetworkClient#getProtocolVersion()` — **без NMS и без рефлексии в сторону ViaAPI**. Читается один раз при входе (в регионе игрока) и хранится в состоянии пинга |
| Диагностика | `/pingshield via` — сводка «кто нативный, кто через Via»; `/pingshield profile <игрок>` показывает клиентскую версию и порог с надбавкой |
| Команда надбавки | Она сама входит в `thresholds.overrides`-логику: если у игрока есть право с высоким порогом, берётся максимум здравого смысла |

Проверить, что Via вообще есть, можно так: `/pingshield via` → строка «протокол сервера: N».
Если автоопределение не сработало, число задаётся вручную в `integrations.via.server-protocol`
(его подскажет сам плагин в логе или `/pingshield info`).

## 11. LuckPerms

Подключение — **soft-depend** (компиляция против `net.luckperms:api:5.5`): без плагина всё работает
на правах Bukkit и `thresholds.overrides`, обращения к API изолированы в отдельном классе и просто
не загружаются.

### Персональный порог — правом, без правки конфига

```bash
/lp group mobile permission set pingshield.threshold.4500 true     # группе порог 4500 ms
/lp user Steve  permission set pingshield.threshold.2500 true      # конкретному игроку 2500 ms
/lp user Steve  meta set pingshield-threshold 4000                 # то же через meta (приоритетнее)
```

Права считаются **с контекстами LuckPerms**, поэтому один и тот же игрок может иметь разные пороги
в разных мирах и на разных серверах сети:

```bash
/lp group mobile permission set pingshield.threshold.4000 true server=survival
/lp user Steve permission set pingshield.bypass true world=arena     # обход только на арене
```

Приоритет: **meta → право `pingshield.threshold.<мс>` → `thresholds.overrides` → общий порог.**
Если прав-порогов несколько, берётся **самый строгий (наименьший)** — ослабить защиту случайно нельзя.

### Персональный режим заморозки

```bash
/lp user Alex meta set pingshield-freeze-mode immunity_only   # щит без заморозки: играет, урона нет
/lp user Alex meta set pingshield-freeze-mode teleport        # заморозка без полёта (дружелюбно к AC)
```

Режимы: `passive | teleport | fly | immunity_only | default`.

### Мгновенное применение

Плагин подписан на `UserDataRecalculateEvent` («кэш прав игрока обновлён») — как только админ
поменял права, кэш порога сбрасывается, перезапуск не нужен. Дополнительно есть кэш
`integrations.luckperms.cache-seconds` (по умолчанию 30 с), чтобы не читать данные на каждом тике.

### Диагностика

```
/pingshield perms <игрок>
```
покажет итоговый порог, **источник** значения (meta/право/конфиг), режим заморозки, первичную
группу LuckPerms и значения ключевых прав — именно этим отвечают на вопрос
«почему меня заморозило раньше, чем соседа».

## 12. Анти-абуз: искусственный лаг, шторм по подсетям, хронический пинг

Защита — это ресурс: замороженный игрок неуязвим. Значит, кто-то попробует «выпросить» её
в момент, когда это выгодно. Три детектора ниже появились именно поэтому. Все три работают
на счётчиках и снимках, которые уже есть в горячем цикле, — новых проходов по сущностям нет.

### 12.1. Детект искусственного лага (`abuse.suspicious`)

Идея: настоящий лаг приходит внезапно и не зависит от происходящего в игре. Считаем баллы
**в момент входа в защиту** (не каждый тик), по признакам:

| Признак | Пункт конфига | Баллы по умолчанию |
|---|---|---|
| Активация в бою (`combat.tag-seconds`) | `points.in-combat` | 2 |
| Получал урон за последние N секунд | `points.recent-damage` | 1 |
| Активация на низком здоровье | `points.low-health` (+ `low-health-percent`) | 1 |
| Обычный пинг игрока хороший (медленный baseline) | `points.good-average-ping` (+ `...-ms`) | 1 |
| Уже часто активировал защиту в этом часу | `points.frequent` | 1 |

Сумма ≥ `threshold` (по умолчанию 3) → применяется `policy`:

| Политика | Что происходит с игроком |
|---|---|
| `LOG` (по умолчанию) | защита выдаётся как обычно, факт пишется в `audit.log` |
| `NOTIFY` | то же + уведомление персоналу (`pingshield.notify`) с разбором баллов |
| `NO_FREEZE` | защита выдаётся «щитом без заморозки»: играет, но урона в обе стороны нет — преимущества в PvP не появляется |
| `BLOCK` | защита не выдаётся, пауза `block-cooldown-seconds` (жёстко: ложное срабатывание = игрок без защиты) |

Почему по умолчанию `LOG`: у честного игрока с плохим каналом тоже бывают «неудачные» активации
(он и в бою бывает, и на низком хп). Админ сначала смотрит статистику в `audit.log`
(`ANTI_ABUSE_SUSPICIOUS`) и включает строгую политику уже осознанно.

Ключевой нюанс: «хороший обычный пинг» считается по **baseline** — очень медленному сглаживанию
(α = 0.02). Один спайк до 5000 ms не сдвинет его с 100 ms, поэтому признак не срабатывает
у всех подряд (см. тест `baselineSurvivesSingleSpike`).

### 12.2. Пинговый шторм по подсетям (`storm`)

Если одновременно лагают несколько игроков **из одной подсети** (IPv4 → `/24`, IPv6 → `/64`) —
это признак проблемы у провайдера или сетевой атаки, а не лага отдельного игрока: один игрок
не может уронить канал соседям. Подсеть вычисляется один раз при входе (снимок в регионе
игрока), группировка — обычная `HashMap` раз в цикл, только по игрокам с высоким «сырым» пингом.

| Политика | Поведение |
|---|---|
| `ALERT_ONLY` (по умолчанию) | персонал получает уведомление, защита продолжает работать |
| `PAUSE_SUBNET` | у игроков этой подсети **не включаются новые защиты**, текущие снимаются, пауза `hold-seconds`; игроку уходит `messages.storm-pause` (объяснение, что проблема в сети, а не в клиенте) |
| `PAUSE_ALL` | то же для всего онлайна (софт-атака через много подсетей) |

Зачем вообще приостанавливать: если канал лёг у всей подсети, заморозить пол-сервера — худший
из вариантов, а защита всё равно не помогает (пакеты не доходят ни туда, ни обратно).
Подсети-исключения — `storm.ignore-subnets` (свои VPN-узлы, известные шумные сети).

Уведомление о шторме — не чаще `alert-cooldown-seconds`, в нём указаны подсети и число игроков,
а событие `PING_STORM` попадает в `audit.log`.

### 12.3. Политика длительного (хронического) пинга (`abuse.chronic-ping`)

Считаются **суммарные** секунды плохого соединения за сессию: счётчик растёт на «плохом» замере
и затухает на хорошем, поэтому разовый спайк не накапливается, а долгий лаг — да. После
`reset-after-good-seconds` стабильно хорошего пинга счётчик и флаги сбрасываются (событие
`CHRONIC_PING_RESET`).

| `action` | Поведение |
|---|---|
| `NONE` | ничего не делать |
| `NOTIFY` (по умолчанию) | сообщение игроку; защита работает как обычно |
| `IMMUNITY_ONLY` | дальше только «щит без заморозки» — не морозим, но и урона нет |
| `KICK` | за `kick-warning-seconds` предупредить и отключить от сервера |

Это честный ответ на «а если у человека просто плохой интернет»: по умолчанию он получает
только сообщение (`chronic-ping-notify`), что это проблема канала/провайдера, а не наказание.
`KICK` рассчитан на хардкорные PvP-серверы, где «вечный щит» сам по себе ломает игру.

### 12.4. Что гарантированно не происходит

* активация в бою не даёт преимущества: при `combat.prevent-protection: false` защита включается,
  но замороженный игрок **не наносит** урон (это свойство самой защиты, не политики);
* «щит без заморозки» не даёт PvP-преимущества: урон выключен **в обе стороны**;
* ложное срабатывание `LOG`/`NOTIFY`/`NO_FREEZE` не наказывает игрока — он просто играет;
* лимит и паузы снимаются, как только соединение стабилизировалось (`CHRONIC_PING_RESET`).

Все решения видны в `plugins/PingShield/audit.log`: `ANTI_ABUSE_SUSPICIOUS`, `PING_STORM`,
`CHRONIC_PING`, `CHRONIC_PING_WARNING`, `CHRONIC_PING_RESET`.

## 13. Тесты и CI

```bash
./gradlew test        # 26 тестов, без запуска сервера
./gradlew build       # компиляция + тесты + JAR
./gradlew simulate    # симуляция поведения на плохих каналах
```

### Что покрыто (JUnit 5, `org.junit:junit-bom:6.1.3`)

| Класс | Что проверяет |
|---|---|
| `PingStateTest` | первый замер, EWMA-сходимость, jitter и надбавку к порогу, гистерезис (серая зона порогов), устойчивость baseline к спайку, накопление/затухание/сброс хронического пинга, окно активаций на 64 записи, «одна задача на снимок» |
| `PingShieldConfigTest` | штатный `config.yml` читается; безопасные значения по умолчанию анти-абуза и шторма; все шесть новых сообщений на месте; `validate()` ругается на бессмысленные комбинации; неизвестная политика откатывается к безопасной |
| `LookupCommandsTest` | формат команд `/co lookup`: тег маркера, минуты/часы, фильтры `a:`/`f:`/`u:`/`r:`, `#count`, и главное — команда для клика **без** ведущего слэша |

Тесты специально написаны на **чистом Java** (`LookupCommands` вынесен из `CoreProtectHook` именно
для этого) — никакой рефлексии и заглушек Bukkit-сервера. Единственное, что нужно из Bukkit, —
`YamlConfiguration` для разбора конфига; `paper-api` подключается как `testImplementation` и в JAR
не попадает.

Побочная польза: тесты нашли реальную хрупкость — `PingShieldConfig` падал при разборе эффектов
(`release.safety.effects`), если реестр Bukkit не инициализирован. Теперь обе стратегии разбора
имени эффекта обёрнуты в `try/catch`, и конфиг не может «уронить» запуск плагина.

### CI (GitHub Actions)

`.github/workflows/build.yml` — на каждый push, PR и вручную (`workflow_dispatch`):

1. `actions/setup-java` → **Temurin JDK 25** (Paper 26.x требует именно 25) + кэш Gradle;
2. `./gradlew build --no-daemon --console=plain` — компиляция, тесты, JAR;
3. артефакт `PingShield-jar` (`build/libs/PingShield-*.jar`, хранение 30 дней);
4. при падении — артефакт `test-report` с HTML-отчётом JUnit;
5. при пуше тега `v*` — отдельная job приклеивает JAR к GitHub Release.

Сборка идёт только Gradle (`build.gradle.kts`), Maven-шагов в workflow нет.
